## 1. Executive Summary

The codebase currently maintains **two distinct signal schemas** that are structurally decoupled and serve different purposes:

| Schema | Location | Purpose | Status |
|--------|----------|---------|--------|
| Legacy `Signal` | `reasoning/signal_engine.py` | Main pipeline production | ✅ Live |
| V1.2 `CanonicalSignal` | `spec/canonical_signal.py` | New architecture blueprint | ⚠️ Partial |
| Extended `CanonicalSignal` | `signal/canonical_signal.py` | Enhanced with validation | 🔴 Dead (no production wiring) |
| `TemporalConvergence` | `spec/temporal_evidence.py` + `temporal/schema.py` | Time alignment | 🔴 Duplicated |
| `ConvergenceArbiter` | `signal/convergence.py` | Multi-signal resolution | 🔴 Dead |

This document proposes a unified signal contract that preserves backward compatibility while enabling migration to the richer V1.2 schema.

## 2. Current Signal Contracts — Fragmentation Analysis

### 2.1 Legacy `Signal` (Production)

**Location**: `src/tongshu/reasoning/signal_engine.py:63`

```python
@dataclass(frozen=True)
class Signal:
    signal_id: str
    ontology_type: str          # ACTION/OUTPUT/CONSTRAINT/RESOURCE/SUPPORT/RELATION/REFLECTION/CHANGE
    direction: str              # INCREASE/STABLE/DECREASE
    polarity: str               # active/neutral/restricted
    strength: str               # low/moderate/high (string, NOT numeric)
    layer: str                  # BASELINE/CYCLE_CONTEXT/DAILY_ACTIVATION
    rule_refs: list
    evidence_refs: list
```

**Characteristics**:
- Lightweight, string-based enums
- Derived from rule matching in `reasoning/signal_engine.py`
- Consumed by `CrossAnalyzer`, `CanonicalComposer`
- **No temporal scope** — layer serves as proxy
- **No confidence value** — strength is ordinal
- **No source engine** tracking per-signal
- Used by: Bazi, Ziwei, Huangli engines via `SignalEngine`

### 2.5 Direction/Polarity Inconsistency

| Schema | Direction Values | Polarity | Strength |
|--------|-----------------|----------|----------|
| Legacy `Signal` | INCREASE/STABLE/DECREASE | active/neutral/restricted | low/moderate/high (string) |
| V1.2 `CanonicalSignal` | POSITIVE/NEGATIVE/CHANGE/NEUTRAL/UNKNOWN | (none) | float 0.0–1.0 |

These are semantically related but not directly mappable:
- `INCREASE` ≈ `POSITIVE`
- `DECREASE` ≈ `NEGATIVE`
- `STABLE` ≈ `NEUTRAL`
- No legacy equivalent for `CHANGE`
- Polarity has no direct mapping in V1.2

## 3. Unified Signal Contract Proposal

### 3.1 Design Principles

1. **Backward Compatibility**: Existing production code must continue to work without modification during migration.
2. **Single Canonical Source**: One schema definition; all consumers import from the same location.
3. **Rich but Minimal**: Include all fields needed for current and planned features; avoid speculative additions.
4. **Validation at Boundaries**: Adapters validate; downstream consumers trust validated data.
5. **Layer Remains as Temporal Proxy**: The 3-layer model (BASELINE/CYCLE_CONTEXT/DAILY_ACTIVATION) is stable and should be preserved.

### 3.2 Proposed Unified Schema

```python
@dataclass(frozen=True)
class Signal:
    """Unified signal contract for the TongShu pipeline."""
    
    # Identity
    signal_id: str                              # Unique identifier
    source_engine: str                          # BAZI|ZIWEI|HELUO|HUANGLI|BLIND|YI|KNOWLEDGE
    
    # Semantic content
    ontology_type: str                          # ACTION|OUTPUT|CONSTRAINT|RESOURCE|SUPPORT|RELATION|REFLECTION|CHANGE
    event_types: List[str]                      # FK → EventDefinition.id (optional, may be empty)
    theme: str                                  # Event theme (optional)
    
    # Quantitative assessment
    direction: str                              # INCREASE|STABLE|DECREASE (legacy-compatible)
    confidence: float                           # 0.0–1.0 (enriches legacy strength)
    strength: str                               # low|moderate|high (legacy-compatible, retained for compatibility)
    
    # Temporal context
    layer: str                                  # BASELINE|CYCLE_CONTEXT|DAILY_ACTIVATION
    temporal_scope: Optional[TemporalScope]     # Rich temporal window (optional, supersedes layer for some uses)
    
    # Provenance
    rule_refs: List[str]                        # Rule IDs that produced this signal
    evidence_refs: List[str]                    # Evidence IDs supporting this signal
    extracted_at: str                           # ISO8601 timestamp
    
    # Conflict resolution (for multi-signal aggregation)
    conflict_group: str                         # Groups signals for conflict resolution
```

### 3.3 Rationale

| Field | Rationale |
|-------|-----------|
| `source_engine` | Replaces `SourceEngine` enum with string for flexibility; allows new engines without schema changes |
| `ontology_type` | Retained from both schemas; the 8 USO types are well-established |
| `event_types` | Links to V1.2 ontology; optional to avoid breaking existing signals |
| `direction` | Uses legacy values (INCREASE/STABLE/DECREASE) for compatibility; can be extended later |
| `confidence` | Numeric confidence enriches legacy string strength; can be derived or independently computed |
| `strength` | Retained for backward compatibility; may be deprecated in future |
| `temporal_scope` | Optional; supersedes `layer` when rich temporal data is available |
| `conflict_group` | Enables Phase 4 multi-engine conflict resolution |

### 3.4 Key Decisions

1. **Keep `layer` as primary temporal proxy**: The 3-layer model is deeply embedded in the pipeline. `temporal_scope` is optional and supplementary.

2. **Preserve legacy `direction` values**: INCREASE/STABLE/DECREASE mapping is well-tested. The V1.2 POSITIVE/NEGATIVE/CHANGE/NEUTRAL/UNKNOWN is richer but not yet adopted. Migration can introduce a mapping layer.

3. **Add `confidence` alongside `strength`**: This allows gradual enrichment without breaking existing code. `strength` remains for legacy compatibility.

4. **Make `event_types` optional**: Not all legacy signals have V1.2 event mappings. The field can be populated during migration.

5. **Remove duplicate `TemporalConvergence`**: Consolidate to single definition in `spec/temporal_evidence.py`.

## 4. Migration Path

### 4.1 Phase 1: Adapter Bridge (No Breaking Changes)

**Action**: Create a compatibility layer that allows both schemas to coexist.

```python
# New module: src/tongshu/reasoning/unified_signal.py

from dataclasses import dataclass, field
from typing import List, Optional

# Unified schema (proposed)
@dataclass(frozen=True)
class UnifiedSignal:
    signal_id: str
    source_engine: str
    ontology_type: str
    event_types: List[str] = field(default_factory=list)
    theme: str = ""
    direction: str = "STABLE"
    confidence: float = 0.5
    strength: str = "moderate"
    layer: str = "BASELINE"
    temporal_scope: Optional[dict] = None
    rule_refs: List[str] = field(default_factory=list)
    evidence_refs: List[str] = field(default_factory=list)
    extracted_at: str = ""
    conflict_group: str = ""

# Backward compatibility converter
def to_legacy_signal(unified: UnifiedSignal) -> 'LegacySignal':
    """Convert UnifiedSignal to legacy Signal format."""
    return LegacySignal(
        signal_id=unified.signal_id,
        ontology_type=unified.ontology_type,
        direction=unified.direction,
        polarity=_direction_to_polarity(unified.direction),
        strength=unified.strength,
        layer=unified.layer,
        rule_refs=unified.rule_refs,
        evidence_refs=unified.evidence_refs,
    )

# Forward compatibility converter
def from_legacy_signal(legacy: 'LegacySignal') -> UnifiedSignal:
    """Convert legacy Signal to UnifiedSignal."""
    return UnifiedSignal(
        signal_id=legacy.signal_id,
        source_engine=_infer_source_engine(legacy),  # Infer from context
        ontology_type=legacy.ontology_type,
        direction=legacy.direction,
        confidence=_strength_to_confidence(legacy.strength),
        strength=legacy.strength,
        layer=legacy.layer,
        rule_refs=legacy.rule_refs,
        evidence_refs=legacy.evidence_refs,
    )
```

### 4.2 Phase 2: Gradual Migration

**Step 1**: Update `SignalEngine` to produce `UnifiedSignal` internally, with `to_legacy_signal()` for output.

**Step 2**: Update `CanonicalComposer` to accept both `Signal` and `UnifiedSignal` (via adapter).

**Step 3**: Migrate `blind_bazi_engine` and `yi/adapter` to use unified schema directly.

**Step 4**: Deprecate legacy `Signal` class; update remaining consumers.

### 4.3 Phase 3: Cleanup

**Action**: Remove legacy `Signal` class, consolidate duplicate schemas.

## 6. Open Questions for Review

1. **Should `strength` be deprecated in favor of `confidence`?**  
   - Argument for: `confidence` is more precise (float vs string).  
   - Argument against: Legacy code expects `strength`; breaking change.

2. **Should `direction` values be unified to V1.2 (POSITIVE/NEGATIVE/CHANGE/NEUTRAL/UNKNOWN)?**  
   - Argument for: More expressive, aligns with event ontology.  
   - Argument against: Requires mapping layer; legacy tests expect INCREASE/STABLE/DECREASE.

3. **Should `temporal_scope` replace `layer` entirely?**  
   - Argument for: Richer temporal representation.  
   - Argument against: `layer` is deeply embedded; `temporal_scope` adds complexity.

4. **How to handle `polarity` (active/neutral/restricted)?**  
   - Option A: Map to `direction` (active→INCREASE, neutral→STABLE, restricted→DECREASE).  
   - Option B: Keep as separate field with nullable.  
   - Option C: Drop in favor of `confidence`.

---

## 7. Recommendations

1. **Start with Phase 1 adapter** — lowest risk, immediate benefit.
2. **Preserve legacy `direction` and `strength`** during migration to avoid breaking tests.
3. **Deprecate `spec/canonical_signal.py` and `signal/canonical_signal.py`** in favor of unified schema.
4. **Consolidate `TemporalConvergence`** to single canonical location (`spec/temporal_evidence.py`).
5. **Add `confidence` as optional enrichment** — do not require for legacy signals.
