    ├── ref_meridian = UTC_offset × 15° (e.g., UTC+8 → 120°E)
    ├── longitude_correction = (location_longitude - ref_meridian) × 4 min/°

    ↓
[Phase 3] Equation of Time (EoT)
    ├── Meeus simplified series (±20 min range)
    ├── EoT = apparent_solar - mean_solar
    └── Total correction = longitude_correction + EoT
    ↓
[Phase 3 cont.] Apparent Solar Time
    ├── solar_datetime = civil_datetime + total_correction
    ├── Validated: solar = civil + corrections["total_correction_min"]
    └── When apparent_solar=False: solar = civil (wall clock)
    ↓

    ├── DAY_BOUNDARY = 23 (子初换日)

    └── 23:59 → next day
    ↓

    ├── bazi_view = (effective_date.year, month, day, effective_hour)

    ↓

    ├── Year Pillar: sxtwl.getYearGZ()

## Critical Realization: True Solar Time Effect on Day Boundary

### The Key Insight

The day boundary check uses **effective_hour** (apparent solar time), NOT civil time. This creates important edge cases:

**Example: Beijing (UTC+8, longitude 116.41°)**
- Total correction ≈ -28 minutes (longitude -14.36 + EoT -13.85)
- Civil 23:00 → Solar 22:31 → No day swap (hour < 23)
- Civil 23:59 → Solar 23:31 → Day swap occurs (hour ≥ 23)

This means:
1. **Not all civil 23:00 inputs trigger day swap** — only those where solar time also crosses 23:00
2. **Some civil 00:00 inputs may map to previous day** — if solar correction is negative enough
3. **The boundary is "soft"** — dependent on location and date (EoT varies)

### Test Evidence

```python
# Civil 23:00 in Beijing
resolved.effective_hour = 22  # Solar time is 22:31
resolved.day_rolled = False   # No swap!

# Civil 23:59 in Beijing
resolved.effective_hour = 23  # Solar time is 23:31
resolved.day_rolled = True    # Swap!
```

This is **correct behavior** — the day boundary rule applies to apparent solar time, which is what traditional bazi calculations use.

## Limitations and Open Items

### 1. Authority Closure Not Yet Complete

While the **algorithm** is correct, we have not yet:
- Cross-verified sxtwl's solar term times against authoritative sources (紫金山天文台, NASA JPL)
- Established sxtwl as the official Calendar Authority
- Documented the provenance chain for each solar term time

### 2. Time System Precision

The current implementation uses:
- Meeus simplified EoT series (accurate to ~1 minute)
- No leap second handling
- Fixed longitude values from location registry (no GPS precision beyond 0.01°)

For production use, consider:
- Using sxtwl's built-in EoT calculation
- Adding leap second support
- Dynamic location precision based on input method

### 3. Historical Date Range

TimeResolver may not support dates far in the past (pre-1900). Canonical cases work because:
- BaziEngine.compute() handles historical dates directly
- TimeResolver is primarily for modern use cases
